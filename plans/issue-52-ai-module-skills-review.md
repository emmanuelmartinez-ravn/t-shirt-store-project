# PRD: AI Module Skills Review (GitHub Issue #52)

## Summary

This repo's two orchestration skills — `do-work` (tail-end verify+commit) and `add-endpoint` (front-half endpoint scaffolding) — were reviewed in issue #52 and found to have one real authorization defect (a commit-only request can push) and several under-specified decision points that already caused a shipped bug (the `promos` domain's GET routes were wrongly guarded). This PRD defines the requirements to fix the push defect, make `add-endpoint`'s decisions structurally explicit instead of advisory, trial an alternative implementer/reviewer delegation model against today's split, rename `do-work` to `verify-and-commit`, and document both skills' history as `docs/ai-module/writeup.md`.

## Problem

Issue #52 (reviewing PR #51 at commit `9740abc`) identified, verified against the current repo state:

1. **A commit-only request can push without authorization.** `do-work/SKILL.md` states in its intro that it does "**not**" push or open a PR, and its Boundary section repeats "Doesn't push or open a PR." But its own step 4 says to follow `.claude/skills/commit/SKILL.md` "exactly," and that skill's step 8 (verified: `.claude/skills/commit/SKILL.md:22`) does push — `git push -u origin <branch>` / `git push`, skipped only on `main`. This is a genuine contradiction in the shipped skill text, not a hypothetical: following `do-work` step 4 literally pushes, despite the skill's own explicit promise not to. No push has actually been executed by this contradiction (source finding only), but the risk is real. Separately, `.claude/skills/pr/SKILL.md` step 5 already pushes independently and unconditionally as part of opening a PR, so `/commit`'s push step is redundant with `/pr`'s — it serves no purpose `/pr` doesn't already cover, while being the actual source of the authorization gap.

2. **`add-endpoint`'s decision points are advisory prose, not a forced structure, and this already produced a real defect.** Verified against `src/promos/`'s controller history: the `promos` domain was originally implemented (by `backend-engineer`, orchestrated by `add-endpoint`) with all three GET routes guarded (`@UseGuards(JwtAuthGuard, PoliciesGuard)` + `@CheckPolicies(...)` + `@ApiBearerAuth()`), then had to be fixed in commit `9740abc` ("fix: make promos GET routes public") by deleting those decorators to match the public-catalog pattern already established by `src/categories/` and `src/products/`. Commit `b70f2d9` ("docs: require asking per-GET auth visibility in add-endpoint skill"), landed immediately before `9740abc`, was a first attempt at preventing exactly this — but it only added prose telling the orchestrator to "ask," with no structural mechanism forcing that question to be answered before delegation. Verified against the live codebase: this repo actually uses three distinct route-access shapes, not two — (a) fully public (no auth decorators at all, e.g. `src/categories/presentation/controllers/categories.controller.ts` GET handlers), (b) authenticated + CASL-checked (`@UseGuards(JwtAuthGuard, PoliciesGuard)` + `@CheckPolicies((ability) => ability.can(Action.X, 'Subject'))`, e.g. `src/roles/presentation/controllers/roles.controller.ts`), and (c) authenticated-only with manual ownership checks (`@CheckPolicies(() => true)`, real authorization done in the use-case, used by self-service routes like `PATCH /users/password`). `add-endpoint/SKILL.md`'s current step 1 mentions per-route auth but doesn't force this three-way classification, and neither it nor `.claude/agents/backend-engineer.md` mentions that a CASL-checked route also requires registering a new subject in the `AppSubjects` union and adding `can()` grants per role in `src/authorization/ability/casl-ability.factory.ts` — a distinct wiring step separate from writing the controller decorators. The skill also currently: doesn't state Prisma model reuse/extend/create criteria as an applicable rule; says to "optionally" smoke-test rather than triggering on an actual coverage gap; and doesn't check whether port 3000 is already occupied before starting `pnpm start:dev`.

3. **No comparison exists between today's delegation split and an adversarial-review alternative.** Today, `add-endpoint` delegates implementation to `backend-engineer` and test coverage to `test-engineer`, with `test-engineer` writing tests against `backend-engineer`'s own handoff summary. Issue #52 observes this means test coverage is written *to* what was implemented, not *against* the original brief — so a mismatch between the brief and the implementation (exactly the shape of the `promos` incident) has no dedicated check catching it. It proposes trialing a fresh reviewer that checks the diff against the brief directly, but explicitly requires comparing outcomes before adopting it as a default, not a blind swap.

4. **`do-work` trusts self-reported and completion-promise text instead of scripted results.** Verified against `do-work/SKILL.md` and the vendored `ralph-loop` plugin (`~/.claude/plugins/marketplaces/claude-plugins-official/plugins/ralph-loop/`): the plugin's Stop hook checks `iteration >= max_iterations` *before* checking whether the last message's `<promise>` text matches — so a loop that exhausts its iteration budget exits silently, with no promise ever verified true or false. `do-work` already has prose warning about this, but every gate in the skill (baseline check, pre-commit re-check) currently relies on the agent's own reading of raw `pnpm lint && pnpm test` output rather than an unambiguous, scriptable signal. The skill also doesn't explain *why* a Ralph Loop is used at all over a manual retry within one turn — the issue asks for that rationale plus a recovery example. Separately, the issue suggests the name `do-work` doesn't communicate its actual scope (verify + commit, not push/PR) as clearly as an explicit name would.

5. **No record exists of this work as a reviewable module.** `docs/` does not exist anywhere in this repo (verified via glob), nor does any git history reference an "AI module," "assignment," or "writeup" (verified via `git log --all --grep`). Confirmed with the user: "the AI module" refers to this repo's two orchestration skills (`do-work`/`verify-and-commit` and `add-endpoint`) themselves, and no external assignment document exists to pull from — this PRD's own resulting work *is* the content to document.

## Goals

- `do-work` (renamed `verify-and-commit`) never pushes under any documented invocation path, and `/commit` never pushes either — pushing exists only in `/pr`.
- `add-endpoint` forces, rather than merely suggests, a decision on: per-route access classification (including CASL subject/grant registration when applicable), Prisma model reuse/extend/create, and when a smoke test is required — captured in a single delegation contract passed verbatim to the implementing agent, instead of ad hoc prompt prose.
- `add-endpoint` checks for a port-3000 conflict before starting the app and cleans up only what it started.
- An implementer+reviewer delegation mode exists as an explicit, opt-in alternative to the current `backend-engineer`/`test-engineer` split, sharing identical requirements-gathering so any outcome difference is attributable to the delegation split itself — with a documented one-time comparison informing (not presupposing) whether it should ever become the default.
- `do-work`/`verify-and-commit`'s pass/fail verification is driven by an actual scripted exit-code check, not by the agent's own reading of command output or a Ralph Loop completion-promise string.
- The rationale for using a Ralph Loop at all (vs. manual single-turn retry) is documented, with a concrete recovery example and an explicit statement of iteration-exhaustion behavior.
- `docs/ai-module/writeup.md` exists, documenting both skills' history, contribution, and the `promos` incident as concrete failure/success evidence, plus a genuine fresh-session demonstration performed after the fixes above are implemented.

## Non-Goals

- No changes to application/domain code, Prisma schema, or any existing API endpoint's actual behavior — this PRD is scoped entirely to `.claude/` skill and agent definitions, one new shell script, and one new docs file.
- Not making the implementer/reviewer delegation mode the default — it ships as an explicit opt-in trial; adopting it as the default is a separate decision made after the one-time comparison, informed by this PRD's work but not decided by it.
- Not mandating TDD as a house-wide process — the issue's TDD aside applies only to the trial-mode `implementer` agent's opportunistic evidence capture, not to `backend-engineer`/`test-engineer`'s existing workflow.
- Not fabricating "fresh-session run" evidence during this PRD or its implementation planning — that evidence can only be produced by actually running the finished skills in new sessions after they're built, and `docs/ai-module/writeup.md`'s corresponding section is written last, from that real evidence.
- Not attempting a live push against this repo's real GitHub origin to demonstrate the push/commit separation — verification uses an isolated local sandbox (a throwaway bare repo standing in for "the remote") instead.
- Not changing `.claude/skills/pr/SKILL.md` — it already pushes independently and correctly gates on `main`; nothing here depends on or alters its behavior.

## Proposed Solution

### 1. Push authorization fix

`/commit` stops pushing, unconditionally — its final step becomes "confirm `git status` is clean," with the existing "ask if grouping is ambiguous" guidance retained as its closing step. Because `/pr` already pushes independently and unconditionally as part of its own flow, this is a pure removal with no loss of capability anywhere. `verify-and-commit` (renamed from `do-work`) needs its commit step to state explicitly that `/commit` never pushes, so that a future edit to `/commit` can't silently reintroduce this contradiction by omission.

### 2. `verify-and-commit` (renamed from `do-work`): scripted verification gate

A small, read-only shell script becomes the single source of truth for "is the working tree green," replacing the skill's current reliance on the agent's own reading of `pnpm lint`/`pnpm test` output. Its required behavior:
- Confirms prerequisites (inside a git repo, `pnpm` available, something actually changed) and fails distinctly and legibly for each.
- Runs both lint and test — always both, regardless of whether lint failed, so a single check surfaces every failure class at once rather than one iteration of a fix cycle at a time.
- Emits one unambiguous final signal (pass vs. which check(s) failed) that both the agent and a bounded fix-and-retry loop can gate on programmatically, with a matching process exit code.
- Never modifies anything or attempts a fix itself — diagnosis and fixing remain the agent's responsibility.

The skill's baseline check, its fix-and-retry loop, and its pre-commit gate all key off this script's output instead of raw command output or an assumption that an earlier iteration's result still holds. The skill also gains a short explanation of what a Ralph-Loop-driven fix cycle buys over manual single-turn retry (each iteration is a fresh, disk-state-grounded re-invocation, so a flawed fix from one iteration doesn't compound into the next) with a concrete example, plus an explicit statement that hitting the iteration cap always ends the loop without ever checking whether the completion promise held — which is exactly why the commit gate must check the script's actual last result rather than trusting the loop's own exit.

The rename to `verify-and-commit` requires updating: the skill's own directory, frontmatter, and internal self-references, plus every cross-reference found elsewhere in this repo — verified to be exactly `add-endpoint/SKILL.md`'s four mentions of `do-work` (its intro line describing itself as `add-endpoint`'s "orchestration companion," its Boundary section, its final report step, and its Common Pitfalls section). No other file in `.claude/` or `CLAUDE.md` references `do-work` by name.

### 3. `add-endpoint`: forced decisions via a delegation contract

Today's step 1 (gather requirements) and step 3 (Prisma schema angle) become the source of a single structured delegation contract — covering the endpoint's outcome, scope, per-route method/path/access-classification/input/success/failure shape, the model reuse-vs-extend-vs-create decision and its ownership/cardinality, acceptance cases, references to a proven existing shape to copy, and an explicit list of anything left genuinely unresolved — that gets handed to the implementing agent verbatim, replacing today's ad hoc prompt prose. Per-route access must be classified into exactly one of the three shapes this codebase actually uses (public / authenticated+CASL-checked / authenticated-only ownership-checked), decided independently for GET vs. write routes, with CASL subject/grant registration resolved as part of that same classification rather than left for the implementer to infer. The skill also gains a mechanical rule for the Prisma reuse/extend/create decision (same entity+lifecycle → reuse; new attributes on that lifecycle → extend; independent lifecycle → new model), a trigger-based (not "optional") smoke-test requirement whenever the automated test suite doesn't already exercise the HTTP layer/guards/validation end to end, and a port-3000 conflict check before starting the app that only ever stops a process the workflow itself started.

Ownership and stopping-rule statements (what this skill does and doesn't own) get consolidated into a single Boundary section that links to `CLAUDE.md`/`.claude/project/architecture.md`/the CASL ability factory rather than restating any of them.

### 4. Implementer/reviewer delegation-mode trial

`add-endpoint` gains a second, explicitly opt-in delegation mode alongside the current default. Both modes share identical requirements-gathering (the delegation contract above); only the delegation step itself differs — this is what makes a later comparison meaningful, since any difference in outcome is attributable to the delegation split rather than to different information being gathered. In the trial mode, a new implementer role owns both the implementation and its own test coverage as a single unit of work (distinct from today's `backend-engineer`, which is explicitly barred from touching test files as a load-bearing part of its own definition — this is a new, separate role rather than a conditional exception bolted onto an existing one), and a new reviewer role checks the resulting diff directly against the original delegation contract and the coordinator's own independent check results — not against the implementer's account of its own work — reporting findings without fixing anything itself.

A one-time, documented comparison (not a new standing process) runs both delegation modes against the same representative endpoint addition — deliberately shaped like the `promos` incident (a mix of public and CASL-guarded routes) so it actually exercises the failure mode the trial exists to catch — and compares defects found, false positives, cost, coverage parity, and how actionable the reviewer's findings are. The outcome informs, but does not by itself decide, whether the trial mode should ever become the default; the current split remains the default regardless of the comparison's outcome until a separate decision is made.

### 5. `docs/ai-module/writeup.md`

A new file documenting this work as a reviewable unit: the repo's starting commit, the commit each of the two orchestration skills was introduced at, what each skill's contribution is, the `promos` incident as concrete failure-then-fix evidence (including the fact that a first, prose-only remediation attempt did not prevent the recurrence, motivating this PRD's structural fix), and — added only once genuinely produced, after implementation — a fresh-session demonstration of both skills running correctly with no memory of the work that built them.

## Alternatives Considered

- **Make `/commit`'s push an opt-in flag instead of removing it outright.** Rejected: `/pr` already pushes unconditionally and independently as part of its own flow, so there is no remaining use case a flag would serve that isn't already covered — removing the step entirely is a strictly simpler invariant ("`/commit` never touches the remote") than a flag that defaults off but could be re-enabled.
- **Fix the CASL-subject-registration gap by editing `backend-engineer.md` to always check `casl-ability.factory.ts`.** Rejected in favor of resolving it during `add-endpoint`'s requirements-gathering instead: `backend-engineer` starts every invocation without memory of the broader feature intent, so it can't independently determine which roles should or shouldn't gain access to a new subject — that's a product decision that has to be made and handed down, not inferred mid-implementation.
- **Make the implementer/reviewer trial a separate parallel skill instead of a mode flag inside `add-endpoint`.** Rejected: a separate skill risks its own requirements-gathering steps drifting out of sync with `add-endpoint`'s over time (edits made to one and not the other) — the same class of problem `b70f2d9`'s failed prose-only patch demonstrates. A single skill with a mode flag guarantees the two paths share identical requirements-gathering by construction, which is required for the later comparison to be meaningful.
- **Make `backend-engineer` conditionally allowed to write `*.spec.ts` files when running in trial mode**, instead of introducing a wholly separate `implementer` agent. Rejected: `backend-engineer`'s prohibition on touching test files is stated in its frontmatter and structurally assumed by its "hand off to test-engineer" section — making it conditional on a runtime flag would make that guarantee only conditionally true for the default path too, which is a worse outcome for auditability than maintaining two small, distinct agent definitions.
- **Keep the name `do-work`.** Considered as the lower-effort option (no directory move, no reference updates). The user chose to rename to `verify-and-commit` instead, favoring a name that states the skill's actual scope (verify, then commit — never push/PR) over minimizing edit surface.
- **Document the implementer/reviewer split as a deferred idea rather than building and trialing it.** Considered as the lower-scope option, consistent with the issue's own "compare outcomes before adopting" framing suggesting it isn't meant to ship blind. The user explicitly chose to design and trial it now rather than defer it.

## Scope / Affected Areas

No `src/<domain>/` application code, Prisma schema, or migrations are touched. Affected paths:

- `.claude/skills/commit/SKILL.md` — remove the push step.
- `.claude/skills/do-work/` → renamed to `.claude/skills/verify-and-commit/` — rewritten steps, new Ralph Loop rationale, updated to gate on the new script.
- `.claude/skills/verify-and-commit/scripts/verify.sh` — new file.
- `.claude/skills/add-endpoint/SKILL.md` — new Boundary section, restructured requirements-gathering steps, new delegation-contract step, new Delegation-mode section, updated re-verify step, updated common pitfalls, and its four `do-work` references updated to `verify-and-commit`.
- `.claude/agents/implementer.md` — new file, used only by `add-endpoint`'s trial mode.
- `.claude/agents/reviewer.md` — new file, used only by `add-endpoint`'s trial mode.
- `docs/ai-module/writeup.md` — new file and new top-level directory.
- `plans/issue-52-ai-module-skills-review.md` — this document.

## Success Criteria

- Running `/commit` (directly, or as invoked by `verify-and-commit`) on a branch with pending changes leaves any remote unchanged, verified against an isolated local sandbox (not the real origin) rather than asserted.
- `verify-and-commit`'s verification script correctly reports pass/fail (and which check failed) against deliberately broken inputs (failing lint only, failing tests only, both, and a genuinely green tree), and `verify-and-commit/SKILL.md` never commits on anything but a fresh pass from that script.
- `add-endpoint/SKILL.md`, run against a new endpoint request with a genuinely mixed public/CASL-guarded route set, produces a complete delegation contract with no route's `access` field left ambiguous, and correctly identifies whether `AppSubjects`/CASL grants need registration — with nothing resembling the `promos` incident recurring.
- The one-time implementer/reviewer comparison is actually run (not merely designed) and its results — defects found, false positives, cost, coverage parity, actionability — are written up for the user's own adopt/reject decision.
- `docs/ai-module/writeup.md` exists with a real fresh-session demonstration of both renamed/updated skills, performed after — not fabricated during — implementation.
- No push, commit, or PR happens as a side effect of building any of the above without separate, explicit authorization at the time.

## Risks & Open Considerations

- Adding `docs/ai-module/` introduces this repo's first `docs/` directory; it is scoped narrowly to this one writeup file per the issue's explicit ask, not a new general documentation location.
- The implementer/reviewer trial roughly doubles delegation cost (two agents instead of one) whenever it's explicitly invoked; it is opt-in specifically so this cost is only paid when a user chooses to trial it, not on every `add-endpoint` run.
- The one-time comparison's representative endpoint is chosen at execution time (deliberately mixed-access, `promos`-shaped) rather than fixed now, since no such endpoint is currently pending — the comparison's validity depends on that shape being genuinely representative of the failure mode under test.
